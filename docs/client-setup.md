# RustDesk GX 客户端填写服务器数据

先按 [服务器部署指南](server-deployment.md) 部署配套 hbbs/hbbr；需要账号时再部署账号 API。控制端和被控端都安装同一套兼容的 GX 客户端，并配置同一个服务器。仅更换一端或使用官方 hbbs，不会自动获得本 fork 的 Native P2P 协调能力。

## 从管理员取得四项数据

| 客户端字段 | 示例 | 填写规则 |
| --- | --- | --- |
| ID 服务器 / ID server | `rd.example.com:21116` | 域名或 IP 加 hbbs 端口，不加 `http://`、`https://` 或路径 |
| 中继服务器 / Relay server | `rd.example.com:21117` | 客户端可达的 hbbr 地址；两者可以是不同主机 |
| API 服务器 / API server | `https://api.example.com` | 仅账号功能需要；包含 HTTPS，不加 `/api`；不使用账号功能时留空 |
| Key | `id_ed25519.pub` 的完整单行内容 | hbbs 公钥，不是私钥文件、远控密码、账号主密钥或 token |

以上是占位示例。若服务端使用 22116/22117，就填真实端口，不要改成示例默认端口。复制公钥时去掉首尾空白，不加引号。

## Windows / Linux / macOS

1. 打开客户端设置，进入“网络 / Network”，如有锁定提示先解锁网络设置。
2. 打开“ID/中继服务器 / ID/Relay server”，填写上表中的 ID、中继、Key；按需填写 API。
3. 保存并返回主界面，等待状态变为“就绪 / Ready”。在另一台设备填写同样的数据。
4. 使用被控端的设备 ID 发起连接；按被控端的确认或远控密码完成授权。服务器账号登录不代替这一步。

macOS/iOS 保留自身支持的原有连接方式；本 fork 的额外 Native P2P 等待控制器目前针对 Windows、Linux、Android，不承诺在 macOS/iOS 上提供同样的行为。iOS 发布的是未签名归档，需要自己的 Apple 签名才能安装。

## Android

在“设置”中的“ID/中继服务器”填写相同字段并保存。若需要作为被控端，还要按客户端提示启动屏幕共享并授予系统所需权限；仅填写服务器地址不会自动开启屏幕共享。账号登录和远控授权是两件事。

## Native P2P 与中继的选择

使用自建服务器的 Windows/Linux Flutter 或 Android 客户端时，在网络设置中找到“启用 UDP 打洞 (Native P2P beta)”。该 fork 默认启用；两端均需允许此功能，hbbs 需启用 `NATIVE_P2P`，且没有强制中继策略。下面的持续等待面板适用于这些前端；Sciter 与命令行保留一次尝试和原回退方式。

- 图形界面会先尝试 Native UDP 打洞与 KCP，展示网络候选、阶段和每轮结果。单轮最长约 60 秒，暂时性失败按 2、5、10 秒退避后继续新一轮；没有总轮数上限。
- 直连受 NAT、防火墙、UDP 限制等影响，不保证一定成功。明确拒绝、签名问题或已认证的无策略结果会停下来等待决定。
- 想立即使用服务器转发时，点击“中继连接”；客户端清理本轮资源后改走现有中继路径。选择只作用于当前逻辑会话，不修改保存的长期中继偏好。
- 关闭等待窗口/取消会清理当前尝试；关闭 Native P2P 会回到原连接路径。显式代理、WebSocket 或强制中继策略会跳过这套原生尝试；命令行/有限诊断接口仍保留原来的一次尝试和回退方式。

系统使用 TUN 本身不等于 RustDesk 配置了显式代理；是否能直连取决于实际路由和网络策略。不要把一次 UDP 回包、面板候选地址或代理界面的 `DIRECT` 当成远控已经通过 P2P 的证据，应确认实际会话的连接类型和远控画面。

## 可选账号登录

API 必须通过受信任的 HTTPS 提供服务，hbbs 开启 `HBBS_ACCOUNT_HANDSHAKE=Y`。填写 API 后，在客户端原有的登录入口输入服务器管理员创建的账号和密码；另一台设备配置同一 API 后登录，可使用该账号的设备列表和地址簿。

这不是官方 Server Pro；不提供等价的组织权限控制，也不将账号 token 当作设备远控授权。登录后若远控失败而退出账号可连接，优先核对 hbbs 握手开关、配套版本和公钥。

## 更新提示

客户端分别显示“上游发布了新版本”和“本 fork 有可下载更新”。只有管理员合并上游、构建完成并手动发布本 fork 的正式 Release 后，才会出现本 fork 的下载入口。点击下载打开本 fork Release 页面，手动选择当前平台客户端；页面里的服务端包只供管理员部署，不安装到客户端。

同一 Release 中包含服务端附件不会自动升级服务器、迁移数据库或修改客户端服务器地址。官方版/其他签名 APK 首次切换到本 fork 时可能需要卸载旧 APK，先备份设置；此后 fork 固定签名允许正常升级。
