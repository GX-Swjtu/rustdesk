# P2P-first connection waiting (2026-10-14)

## Behavior

Windows/Linux Flutter and Android graphical ID connections use one continuous
controller when native P2P is enabled. Remote desktop, file transfer, terminal,
camera and the desktop forwarding/RDP pages share the same controller and panel.
Only connection types already available on each platform are exposed.

Each round acquires the local native permit and a new signed session (hbbs also
enforces its existing one-attempt-per-device gate across client processes),
rediscovers UDP mappings and requests a strategy from the existing score table.
It has a 60-second absolute budget, shortened by the server ticket. Local work
reserves 1.5 seconds for teardown. Strategy windows (at most 38 seconds), the
three-second KCP reserve, 257 sockets and 8192 packets are unchanged. Consecutive
retry delays are 2, 5, 10, 10... seconds; there is no total round limit.

Silence, packet loss, busy devices and unclassified transport errors retry.
Missing or stale peer registration also retries, including an ambiguous
`Unsupported` reply from an older coordinator. A fresh signed refusal, invalid
identity/signature or authenticated no-strategy result stops probing and waits
for a user decision. An unknown capability never claims incompatibility.
Disabling native P2P during a wait cleans up the current attempt and returns to
the original connection path.

**Relay connection** is accepted once in the controller, finishes local cleanup,
then uses the existing forced-relay connection path. It remains in this window's
memory across reconnects and new forwarding connections. It never changes
`peer_relay` or calls `reconnect(true)`. Closing the logical session resets it.
Already established forwarding transports are not migrated.
Closing a window or deleting a mapping can still cancel a chosen relay while
cleanup is pending. Cleanup completion and cancellation serialize the final
handoff; a cancelled flow cannot start the relay fallback.

The CLI and finite diagnostic API retain one attempt and automatic legacy
fallback. Explicit proxy, WebSocket and forced-relay policy bypass native work.
Android gains no foreground, Wi-Fi, permission or service requirement.

## Ownership and diagnostics

`src/native_p2p/waiting.rs` owns window decisions, independent transport IDs and
round generations. Direct delivery and relay/cancel acceptance use the same lock
order. A removed forwarding mapping invalidates its generation, including after
the same local port is recreated. A new round cannot start from an old mapping.
Closing one shared terminal view follows the existing view reference count.

A round owns its permit, optional Android registration, signed lease, UDP probe
futures and KCP pump. Probe futures are polled by their owner rather than detached
tasks: cancellation drops all losing futures and restores socket TTL. KCP abort
is joined before cleanup returns. Session cancellation and Android withdrawal
each have a 500 ms notification bound. Drop cleanup is only the emergency path.
An unacknowledged remote cancellation is bounded by ticket expiry. After KCP
handoff the original RustDesk session owns authentication and business lifetime.

The common library keeps existing APIs and adds optional progress observation.
No protobuf, capability name, strict plan field or listening port changes.
Structured no-strategy/refusal diagnostics use the existing signed Error string, prefixed
`native-p2p-reason:` and bounded to 3072 JSON bytes. Only validated candidate
addresses are included; old text errors remain readable.

The new Flutter component replaces only connection waits, not generic loading
dialogs. Visible views read the latest snapshot every 500 ms with at most one
request in flight. Background visibility stops UI polling only. Per transport it
retains 20 round summaries and 200 stage records; the window also bounds retained
completed transports. Old round reports and disposed-widget reads are ignored.
Password, confirmation and permission dialogs are not reopened by progress.

Snapshots contain candidate addresses in observation order, network evidence,
roles, TTL, delay, authenticated UDP counters and stage timing. They contain no
passwords, private keys or probe keys. UDP response, KCP and device authentication
are distinct milestones, with no overall success percentage.

## Reproducible checks

Use the existing toolchains and dependency locks described in README.md. No
public dependency is added or upgraded by this change. Generated bridge outputs
remain generated/ignored according to the repository's existing policy.

```powershell
cargo test --offline --manifest-path libs/hbb_common/native-p2p/Cargo.toml --lib
cargo test --locked --offline --release --lib --features flutter,hwcodec native_p2p -- --test-threads=1
cargo test --locked --offline --release --lib --features flutter,hwcodec port_forward -- --test-threads=1
cd flutter
flutter test --no-pub test/native_p2p_waiting_test.dart
flutter build windows --release --no-pub
```

The Windows test build uses the existing E: Cargo cache, VCPKG_ROOT and
LIBCLANG_PATH. Generate bindings with flutter_rust_bridge_codegen 1.80.1 before
building the frontend. The artifact directory contains the exact Linux hbbs,
Android cargo-ndk and offline Gradle build scripts/logs and resolved Flutter
3.24.5 build lock; the repository dependency lock remains unchanged.

## Validation record

Evidence is in `artifacts/p2p-waiting-20261014` at the workspace root. Unit tests
cover 1000 simulated rounds (999 transient failures followed by success), exact
backoff intervals, explicit unsupported parking, independent windows/mappings,
stale generations, repeated relay/cancel, shorter tickets and 100 real KCP/socket
cancellations. Widget tests cover narrow screens, no-strategy presentation,
diagnostic copying, one in-flight read, background polling and duplicate clicks.

The existing isolated Linux namespace lab was run against the formal common
module and KCP transport. Direct, prediction, birthday, both-predict, mixed,
multiple exits, LAN and public-address scenarios each passed 10/10 authenticated
KCP sessions. The loss scenario passed 9/10; its first listener failed registration
with `deadline has elapsed`, before punching started. This original failure is
retained in `lab-success/loss-01`. All 90 trials removed their namespaces.
Six rejection/cancellation scenarios passed: both-random, cancel, bad-proof,
blocked, unverified and blackhole. These results are controlled-network evidence,
not substitutes for real Windows/Android acceptance.

Real Windows waiting/relay/cancel and connection-type checks, final build hashes,
installation backups and the 30-minute resource observation are recorded in the
delivery record alongside the packages. Android device acceptance remains a
separate pending item; an APK build does not prove device interoperability.

The real Windows checks kept both TUN adapters enabled. A single connection
survived 13 failed rounds and established authenticated native KCP with a desktop
on round 14 after the test coordinator recovered. Manual relay delivered a
desktop, released probing sockets and left the saved relay preference unchanged.
The final package passed school-to-home at 14:58 and home-to-school at 15:27;
the latter completed in about 15 seconds with no relay socket or server relay
packet during its measured interval. Earlier unrelated relay packets in that
capture are retained and separated by their timestamps.
The 100 MiB native transfer matched SHA-256 on both endpoints. Camera displayed
video; terminal login created its helper/pipes. Both forwarding mappings returned
SSH banners, the established mux remained usable without hbbs, and cancelling one
pending mapping left its listeners and other mapping usable. RDP reached native
transport/login; Windows RDP OS authentication was not automated.

The final Windows package also completed a 1,808.1-second parked-wait observation
with 103 samples. After initial startup, UDP/TCP/relay sockets stayed at zero,
handles ranged from 810 to 826, and private bytes ended at 243,765,248 versus
235,978,752 at the warm baseline. Memory rose while expanding diagnostics, then
fell again; it did not grow continuously. The observation included minimized and
visible periods, not 30 minutes of continuous active probing. The window was
stopped by its verified process ID after the UI helper could not restore it;
that teardown is not counted as an additional normal-cancel test. Continuous
retry and cooperative cancellation have the separate evidence listed above.

Placeholder IDs used for unsupported-peer testing were test-launch arguments,
not product defaults. The test window was stopped and the remembered input was
restored to the real peer. No test placeholder belongs in a startup task or
shipped configuration. `diagnostic-observed-waiting.json` in the delivery directory
is a real snapshot copied through the UI; `diagnostic-example.json` is illustrative.

### Review follow-up

The two review fixes passed 15 Windows client native-P2P tests, including relay
cleanup cancellation for window close/mapping deletion, 1000 retries after an
unknown capability and transient failures, and 100 real KCP/socket cancellations.
Common passed 26 tests on Windows and 25 on Linux; the registration regression
failed against the original coordinator before the fix. Linux hbbs and the
Android arm64 Rust library built in release mode. Logs and build commands are
under `artifacts/review-fixes-20261014`. This follow-up was not installed on the
real endpoints; the device observations above describe the preceding package.

The runtime delta is limited to `native_p2p/waiting.rs` (cancel arbitration and
final handoff), `client/native_p2p.rs` (honor that decision and retry unknown
capabilities), and common's `coordinator.rs` (distinguish missing/stale registration
from a signed refusal). Both common baselines carry the same patch. There is no
new state, dependency, protocol field or legacy-connection refactor.

## Regression surface / minimization

| Existing path touched | Necessary change |
| --- | --- |
| common native-p2p coordinator / transport / hole | Signed no-strategy reasons, bounded 60-second leases, progress observer and explicitly owned cancellable resources; original entry points remain. |
| client/native_p2p.rs and native_p2p.rs | Continuous graphical controller alongside finite callers; per-call cancellation registry and KCP accept cancellation. |
| native_p2p/android_registration.rs / android.rs | Own temporary registration before cancellation can interrupt preparation; await bounded withdrawal. |
| client.rs | Select graphical vs finite native entry point; suppress a user-cancelled forwarding wait error. Legacy connection and authentication code remains. |
| ui_session_interface.rs | Window lifetime and mapping generation hooks; existing close/reconnect and terminal reference counting remain. |
| kcp_stream.rs | New native-only constructor owns and joins the UDP pump; existing constructors keep their behavior. |
| port_forward.rs / port_forward_mux.rs | Keep the KCP handle with the raw pipe or multiplexed tunnel until it ends, instead of dropping it at login return. |
| flutter_ffi.rs / web bridge | Two snapshot/control entry points and unsupported-platform stubs. |
| Flutter desktop/mobile connection pages and models/model.dart | Replace the relevant initial/reconnect waiting call; mount forwarding waits and dismiss progress before existing authentication dialogs. |
| src/lang/*.rs | Append the waiting component's keys according to repository localization rules; existing translations are unchanged. |

No media, codec, input, clipboard, password, permission, JNI, Android lifecycle,
firewall, route, proxy or production-server logic is reworked. Client and server
common baselines stay separate, with the same native-p2p source patch applied.

## Rollback

The General/Android native P2P switch returns to original connection behavior.
To restore the previous test client, run `Update-TestClient.ps1 -Package` with the
saved `previous-client.zip` emitted by installation. This restores both frontend
and DLL. The original-installation `Use-TestClient.ps1 -Mode Restore` is unchanged.
For the isolated test hbbs use the delivered `switch-test-hbbs.py --restore`; it
validates the exact process directory/binary/22116 arguments before replacement.
Production hbbs/hbbr and frp are outside the deployment script's target.
